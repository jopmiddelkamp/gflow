Where gflow runs set-version.sh

gflow runs .gflow/set-version.sh (or .cmd on Windows) at the moments the version changes, and commits whatever it writes. Pick your .gflow/config below; every diagram, step and table adapts. Examples assume production runs 1.3.0, develop already says 1.4.0, and the script only writes the version it is given.

      State after

      Hotfix created without a checkout: with --no-checkout or the worktree flow, gflow creates hotfix/1.3.1 without switching to it, so it cannot commit there. It skips the script and prints ⚠ Version script not run: hotfix/1.3.1 was created without checkout, so gflow cannot commit version files there. with the manual fix: git switch hotfix/1.3.1, run set-version.sh 1.3.1, commit, push.

      The script contract

      One argument, the clean version

      argv[1] is always X.Y.Z, never -rc.N. The working directory is the repo root of the current worktree.

      Clean tree first

      gflow refuses to run the script on a dirty tree, so the version commit never sweeps up your own changes.

      No change, no commit

      If the tree is still clean afterwards, gflow commits nothing. Otherwise it runs git add -A and commits chore: set version X.Y.Z.

      Free vs protected

      Free commits straight to the branch. Protected commits straight only to a branch gflow just created; develop and an existing release branch get the commit through a squash-merged version PR.

      Never at finish or sync

      gflow finish and gflow sync only merge and tag. Reusing an existing release or hotfix branch never runs the script again.

      Failures name the fix

      A non-zero exit stops with the script's stderr. A missing executable bit says chmod +x plus git update-index --chmod=+x. Only the other platform's file present is an error.
